## Decisions resolved by direct source reading

1. **No new ownership/fencing *contract* is needed.** ADR-CAPI-003 already accepts an external persistent ownership record, a monotonic epoch, CAS/equivalent serialization and effective denial at write boundaries. Do not invent an alternative lease protocol in the security ADR. Exact backing implementation and E2E proof remain OPEN.
2. **Cold handover and cold DR already have explicit behavioral constraints.** ADR-CAPI-006 and -007 require no concurrent effective writers, old-owner fencing before activation, and a write-blocked restore target. These are architecture requirements, not evidence that every current external provider and agent channel is fenced.
3. **The backup system is not the live security-fact authority by default.** ADR-CAPI-005 distinguishes Velero/S3 state backups from a separate ownership/audit store. B-17 extends the accepted epoch model to host revocations, consumed grants and retired identities. That extension is **new normative candidate scope**, not an assertion already covered by ADR-003.
4. **No mandatory external epoch on every host API request has been decided.** The accepted ADR requires effective fencing. It does not require a new always-online per-write cross-cluster CAS lookup. The mechanisms must be selected per write boundary and tested with offline/returning hosts.

## Open architectural or engineering questions to carry into the normative ADR

- **Q-1 / B-17:** Can the existing ADR-CAPI-003 independent ownership/audit store be extended for revocation, consumed-approval and enrollment-generation facts with correct atomic ordering and resilience? The source describes a contract, **not** a selected or deployed database.
- **Q-2 / B-12:** Which actual host/agent/SSH/BMC/provider/workload API write endpoints can be fenced without adding new infrastructure? Where must unreachable edge targets be quarantined?
- **Q-3 / B-11:** How will restored K8s management APIs avoid serving old host RBAC before current B-17 revocations are reconciled? A safe activation barrier or authoritative credential invalidation must be tested, not assumed from controller startup order.
- **Q-4 / B-18:** Which KMS/key custody controls and complete-backup encryption are available across the S3/Velero and etcd restore profiles, including outage and key-recovery?
- **Q-5 / B-19:** Who detects lost enforcement or restored unsafe RBAC independently, and which alert paths remain usable during management failure?
- **Q-6 / Existing Platform ADRs:** Reconcile the eventual security ADR against ADR-Platform-030/031/034/035/047/048 and their accepted/proposed statuses. This crosswalk only establishes the **CAPI 001–007** relationship.

## Evidence and maturity boundary

**Nothing here closes G-DR, G-UPGRADE or G-BYOH-ENROLL.** Directly reading an accepted architecture ADR is `DESIGN/SOURCE`, not a `PASS` test. All current v0.2 E2E tests remain NOT-RUN; the source-reported prior Scaleway lab authorization finding is not silently reused as a new negative test.

**Suggested normative ADR posture:** Adopt (by pinned-reference) the security goals, cross-reference ADR-CAPI-003/005/006/007 for management ownership/backup/DR, and leave the enforcement implementation and production gates unresolved until measured. No duplicate management authority subsystem should be mandated solely by the new ADR.
